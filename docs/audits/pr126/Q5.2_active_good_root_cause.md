# Q5.2 — PR7.1 active-good root cause and follow-up contract

## Purpose

This checkpoint records the root cause found after reviewing `main` against the PR126 / PR7 dispatcher stack.

The issue is not that PR7 invented an impossible goods count. The issue is that PR7 preserves the existing generated all-good dispatch shape from `main`, while the Q4 performance model and Q5 target language assumed a future active / relevant-good reduction that has not yet been implemented.

## Finding

The game has fewer than the apparent high runtime-good count reported by the PR7 probe. The high counter shape is therefore not a count of distinct goods in EU5. It is a count of generated per-good helper invocations across repeated country / market / phase scopes.

Example interpretation:

```txt
performance_us00_goods = 222
performance_us10_goods = 222

likely shape:
  3 country-present passes
  x 74 generated goods
  = 222 generated helper calls
```

This does not mean there are 222 goods. It means the current dispatcher still schedules `all_goods` helpers once per country-present pass in the detailed market branch.

## Main-branch behavior

`main` already uses generated all-good dispatcher surfaces:

```txt
modeu5_process_us00_monthly_market_all_goods
  -> modeu5_process_us00_monthly_market_good_<each generated good>

modeu5_process_us10_monthly_market_all_goods
  -> modeu5_process_us10_monthly_market_good_<each generated good>
```

The generated wrappers are intentional because per-good map names and helper names must remain literal identifiers in EU5 script.

`main` already contains inner per-good business gates, but those gates happen after the all-good helper has been invoked.

### US-00 main business rule

For each generated good, the US-00 monthly helper should only do full record work when:

```txt
produced_in_market:<good> > 0
OR previous ModeU5 US-00 record / active state exists
```

This is the business rule to preserve in the refactor.

### US-10 main business rule

For each generated good, the US-10 same-market consumption helper should only resolve stock when:

```txt
country has pending same-market consumption request for that market + good
```

Sparse supplier lists then narrow candidate countries after a good is selected for resolution. They are not themselves the market-good scheduler.

## PR7 / #144 behavior

PR7 changes ownership and flow shape, not the generated good-selection model.

The intended PR7 switch is:

```txt
old live path:
  modeu5_run_us00_monthly_pipeline_all_goods
  modeu5_run_monthly_stock_demand_resolution

new live path:
  modeu5_run_monthly_promoted_market_local_cycle
  modeu5_run_monthly_country_trade_owner_cycle
```

Inside the promoted-market local cycle, the current PR7 implementation still calls the generated all-good helpers:

```txt
modeu5_run_promoted_market_live_local_branch_market_all_goods
  -> rebuild countries_present_in_market once
  -> refresh capacity for countries present in market
  -> every country present in market:
       modeu5_process_us00_monthly_market_all_goods
  -> every country present in market:
       modeu5_process_us10_monthly_market_all_goods
```

Therefore, PR7 should be considered an ownership / live-dispatcher switch, not yet the active-good scheduling optimization.

## Root cause classification

```txt
Not introduced by PR7:
  generated all-good US-00 / US-10 helper dispatch already exists on main.

Preserved by PR7:
  PR7 keeps the all-good dispatch inside the new promoted-market local branch.

Missing from PR7:
  explicit active / relevant-good scheduling before invoking per-good helpers.

Documentation mismatch:
  Q4's `G_a` performance model assumes an active-good set, while PR7 currently still uses `G_supported` helper invocation and relies on inner helper gates.
```

## Correct follow-up target

PR7.1 should not invent a new economic rule. It should carry forward the existing `main` rules and make them explicit as pre-dispatch or measured scheduling criteria.

The target design is:

```txt
promoted-market local branch
  -> rebuild countries_present_in_market once
  -> build or measure active/relevant goods for US-00 and US-10
  -> US-00 only schedules goods where:
       produced_in_market:<good> > 0
       OR previous US-00 active state exists
  -> US-10 only schedules goods where:
       pending same-market consumption request exists
  -> sparse supplier lists still narrow candidate countries after US-10 good selection
```

Until a real active-good queue is safely implemented, PR7.1 should at minimum split counters so logs distinguish helper dispatch volume from meaningful business work.

## Required metric split

Current PR7 counters can make it look as if the game has more goods than it does. The next probe should split:

```txt
US-00:
  us00_goods_considered
  us00_goods_processed
  us00_goods_produced_gate_hits
  us00_goods_previous_state_hits

US-10:
  us10_goods_considered
  us10_requests_processed
  us10_pending_request_hits
  us10_supplier_countries_scanned
```

Definitions:

| Metric | Meaning |
|---|---|
| `*_goods_considered` | Generated per-good helper invocations. This can equal countries-present × generated goods. |
| `us00_goods_processed` | Full US-00 record work actually executed. |
| `us00_goods_produced_gate_hits` | Goods with `produced_in_market:<good> > 0`. |
| `us00_goods_previous_state_hits` | Goods with previous ModeU5 US-00 state requiring cleanup / penalty / ledger continuity. |
| `us10_goods_considered` | Generated US-10 per-good helper invocations. |
| `us10_requests_processed` | Pending same-market consumption requests actually resolved. |
| `us10_pending_request_hits` | Goods with pending request map entry for country + market. |
| `us10_supplier_countries_scanned` | Supplier-country candidate checks after a US-10 request is selected. |

## PR7.1 acceptance criteria

PR7.1 is acceptable when it proves one of these two states.

### Minimal safe PR7.1 — instrumentation only

```txt
- root cause documented;
- counters split considered vs processed work;
- PR7 comparison probe reports both dimensions;
- Q4/Q5 wording corrected so 58x is not implied until `G_a` exists;
- no runtime behavior change outside debug/audit counters.
```

This is safe to stack immediately after PR7 because it does not change economics.

### Full PR7.1 — active-good pre-dispatch

```txt
- US-00 generated all-good dispatch is replaced or guarded by a safe active-good scheduler;
- US-10 generated all-good dispatch is replaced or guarded by a safe pending-request scheduler;
- business rules match `main` exactly;
- zero-production / no-previous-state goods do not run full US-00 record work;
- no-pending-request goods do not run US-10 resolution;
- sparse supplier list semantics remain unchanged;
- fallback markets still use vanilla behavior;
- runtime probe proves considered > processed in normal data and Performance mode narrows both market count and meaningful work.
```

This requires EU5 runtime validation and should not be merged on static review alone.

## Impact on #126 closure

PR7 / #144 can still satisfy the Q5 ownership objective if its runtime proof is clean.

However, the Q4 performance objective should remain open until the active-good gap is closed or explicitly re-scoped:

```txt
Q5 ownership split:
  PR7 / #144 target

Q4 active-good reduction:
  PR7.1+ follow-up target
```

The safe closure language for PR126 should therefore be:

```txt
PR126 reaches the live monthly ownership objective once PR7 is merged and validated.

PR126 should not claim the full `G_a` performance target until PR7.1 or a later stacked PR proves active/relevant-good scheduling, or updates Q4 to state that current PR7 only reduces market ownership and relies on per-good early exits.
```
