# Q4.1 — Intermediate factorisation conclusions after Q5.1

## Purpose

This checkpoint explains the factorisation effort in performance terms for a junior developer. It connects the original Q4/Q5 problem space to the current Q5.1 dispatcher state, then states the target and expected benefits.

The key idea is simple:

```txt
Do not optimise the inner loop first.
First make sure the inner loop runs under the right owner, and only the right number of times.
```

For ModeU5, the correct owner split is now:

```txt
monthly_country_pulse
  -> country prerequisites
  -> market-center-owned local branch
  -> country-owned trade pass
  -> optional reconciliation
```

## Original situation: Q4 and Q5

The original performance problem was not only that some helpers were large. The deeper problem was that broad monthly orchestration made the cost shape hard to see.

| Area | Original concern | Performance risk |
|---|---|---|
| Country pulse | The monthly stock cycle starts from each country | Market-local work can accidentally repeat once per country |
| US-00 / US-10 helpers | All-goods adapters hide a generated loop | Real cost is countries-present × goods |
| Market-country cache | Countries present in a market were not the obvious frame | Code may rediscover countries or scan too broadly |
| Trade loop | `every_trade` is country-scope, not market-scope | Trade must not be nested inside the promoted-market local branch |
| Reconciliation | End-of-cycle repair exists | It must not hide duplicated work or wrong ownership |

Q5 clarified the target ownership: local market work belongs to the promoted/market-center branch, while vanilla trade work remains a country-owned trade pass.

## Current state after Q5.1

Q5.1 records that the live monthly dispatcher now calls the promoted-market local cycle and the country trade-owner cycle instead of the old broad US-00 / US-10 monthly surfaces.

The highlighted nested loops mean:

```txt
every_market_center_in_country
  -> rebuild countries_present_in_market once
  -> every country present: refresh capacity
  -> every country present: run US-00 all generated goods
  -> every country present: run US-10 all generated goods
```

For a junior developer, this is a good shape because the market-local branch is owned by the market center. It is still expensive, but it is expensive in a visible and measurable way.

## How to read the highlighted loops

### Capacity refresh

```txt
for each country present in this market:
  refresh this country × market capacity
```

Cost estimate for one market:

```txt
capacity_cost(m) ~= C_m
```

`C_m` is the number of countries present in market `m`.

### US-00 before consumption

```txt
for each country present in this market:
  for each generated good:
    run US-00 production/admission work
```

Cost estimate:

```txt
us00_cost(m) ~= C_m × G
```

`G` is the number of generated stock goods.

### US-10 same-market requests

```txt
for each country present in this market:
  for each generated good:
    run US-10 same-market consumption work
```

Cost estimate:

```txt
us10_cost(m) ~= C_m × G
```

So one detailed promoted market costs roughly:

```txt
local_market_cost(m) ~= L_m + C_m + 2 × C_m × G
```

Where:

```txt
L_m = locations scanned to build countries_present_in_market
C_m = countries present in the market
G   = generated stock goods
```

Example, not a benchmark:

```txt
L_m = 20
C_m = 3
G   = 50

cache rebuild      ~= 20
capacity refresh   ~= 3
US-00 goods work   ~= 150
US-10 goods work   ~= 150
--------------------------------
local market total ~= 323 coarse work units
```

If the same market-local branch accidentally ran once for each of the three present countries, the rough work becomes:

```txt
3 × 323 = 969 coarse work units
```

That is why the first optimisation target is ownership: process the market once, not once per country that can see it.

```txt
cache_rebuilds_per_market = country_cache_rebuilds / markets_detailed

us10_goods_per_market     = us10_good_scans / markets_detailed
```

Expected dispatcher proof:

```txt

```

## Current state assessment: Q4.1 and Q5.1

| Topic | Original situation | Current state | Intermediate conclusion |
|---|---|---|---|
| Dispatcher ownership | Broad country pulse hid market-local ownership | Live cycle separates promoted-market local and country trade-owner passes | Good structural improvement |
| Market-local branch | Risk of repeated market mutation | `every_market_center_in_country` owns the local branch | Correct direction |
| Countries-present cache | Could be recomputed or approximated | Built once from `every_location_in_market` into `modeu5_countries_present_in_market` | Good work-cache factorisation |
| Capacity | Could be confused with mutation | Capacity remains a prerequisite and country-market relation | Good separation |
| Generated goods | All-goods scan remains expensive | Still all-goods inside detailed markets | Accept for correctness; optimise later with active goods |
| Trade | Could be mixed with market-local work | Kept as country-owned `every_trade` pass | Correct separation |
| Measurement | Mostly qualitative before | PR126 counters expose markets, country passes, goods scans, trade passes | Good enough for shape proof, pending clean runtime logs |

## Target direction

The target is not to remove loops. The target is to put each loop under the correct owner.

```txt
monthly_country_pulse
  -> country prerequisites
  -> promoted-market local branch once per market-center owner
       -> countries present in that market
       -> generated goods for US-00 / US-10
  -> country-owned trade pass
  -> validation / reconciliation
```

Future optimisation order:

1. Prove ownership correctness: each market-local branch runs once per market.
2. Measure the loop shape with counters.
3. Reduce detailed markets through Performance mode.
4. Only then reduce generated-good scans with active-good work lists.
5. Keep stock writes behind central operators.

## Anticipated benefits

| Benefit | Why it matters | Measure |
|---|---|---|
| Less duplicated market-local work | Avoids repeating a market branch for every country present | `cache_rebuilds_per_market ~= 1` |
| Reduced detailed work in Performance mode | Cuts the largest market × country × goods multiplier | Normal good scans > Performance good scans |
| Cleaner ownership model | Junior developers know where to place new logic | Diagram nesting matches code nesting |
| Safer active-good optimisation later | Avoids skipping business-required goods too early | Compare good scans before/after active-good list |
| Trade safety | Trade work stays country-owned and inter-market | Trade passes stable when detailed markets change |

## Practical rule for junior developers

Before changing code, write the loop formula.

For the highlighted section:

```txt
for each detailed market m:
  countries cache    -> L_m
  capacity refresh   -> C_m
  US-00 all goods    -> C_m × G
  US-10 all goods    -> C_m × G
```

Then ask:

```txt
Can I reduce M, the number of detailed markets?
Can I reduce accidental repeats of the same market?
Can I reduce G safely with an active-good list?
```

The safest first win is reducing detailed markets and accidental repeats. The riskiest first win is reducing generated goods, because it can silently skip a good that still needs production, demand, validation, or reconciliation.

## Closure criteria

Q4.1 is an intermediate checkpoint. It is good enough when:

```txt
Q5.1 nested loop ownership matches the code
Normal mode does more detailed/goods work than Performance mode
Performance mode keeps the controlled request satisfied
Trade-owner pass remains one pass in both modes
Runtime logs are clean enough to trust the counters
```

It is not fully closed until active-good filtering, cache ownership, clean-log proof, and full regression proof have landed or have explicit follow-up issues.
