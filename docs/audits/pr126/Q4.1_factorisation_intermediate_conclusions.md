# Q4.1 — Intermediate factorisation conclusions after Q5.1

## Purpose

This checkpoint explains the factorisation effort in performance terms for a junior developer. It connects the original Q4/Q5 problem space to the current Q5.1 dispatcher state, then states the target and expected benefits.

The key idea is simple:

```txt
Do not optimise the inner loop first.
First make sure the inner loop runs under the right owner, and only the right number of times.
```

For ModeU5, the correct owner split is now:

```txt
monthly_country_pulse
  -> country prerequisites
  -> market-center-owned local branch
  -> country-owned trade pass
  -> optional reconciliation
```

## Original situation: Q4 and Q5

The original performance problem was not only that some helpers were large. The deeper problem was that broad monthly orchestration made the cost shape hard to see.

| Area | Original concern | Performance risk |
|---|---|---|
| Country pulse | The monthly stock cycle starts from each country | Market-local work can accidentally repeat once per country |
| US-00 / US-10 helpers | All-goods adapters hide a generated loop | Real cost is countries-present × goods |
| Market-country cache | Countries present in a market were not the obvious frame | Code may rediscover countries or scan too broadly |
| Trade loop | `every_trade` is country-scope, not market-scope | Trade must not be nested inside the promoted-market local branch |
| Reconciliation | End-of-cycle repair exists | It must not hide duplicated work or wrong ownership |

Q5 clarified the target ownership: local market work belongs to the promoted/market-center branch, while vanilla trade work remains a country-owned trade pass.

## Current state after Q5.1

Q5.1 records that the live monthly dispatcher now calls the promoted-market local cycle and the country trade-owner cycle instead of the old broad US-00 / US-10 monthly surfaces.

The highlighted nested loops mean:

```txt
every_market_center_in_country
  -> rebuild countries_present_in_market once
  -> every country present: refresh capacity
  -> every country present: run US-00 all generated goods
  -> every country present: run US-10 all generated goods
```

For a junior developer, this is a good shape because the market-local branch is owned by the market center. It is still expensive, but it is expensive in a visible and measurable way.

## Canonical performance notation

| Symbol | Meaning |
|---|---|
| `C` | Number of countries traversed by a full monthly pulse |
| `M_c` | Average number of markets present in a country |
| `M` | Total number of markets |
| `P` | Number of promoted markets after normal/performance filtering and de-duplication |
| `K_m` | Average number of countries present in a promoted market |
| `G_supported` | Total goods supported by generated adapters |
| `G_market` | Candidate or produced goods in a given market |
| `G_a` | Active goods in a promoted market after filters/cache |
| `T_country` | Trade candidates assigned to one country for the separate country-scope trade pass |

Important nuance:

```txt
G_market = 60 can remain a market-level load assumption.
It is not the total number of goods supported by the mod.
```

A Chinese, African, or European market will not necessarily have the same set of produced or active goods. For performance planning, `G_market` is a broad market-load assumption, while `G_a` is the optimized active-good subset we want the promoted-market branch to reach after filters/cache.

## How to read the highlighted loops

### Capacity refresh

```txt
for each country present in this market:
  refresh this country × market capacity
```

Cost estimate for one promoted market:

```txt
capacity_cost(m) ~= K_m
```

`K_m` is the average number of countries present in promoted market `m`.

### US-00 before consumption

```txt
for each country present in this market:
  for each generated or active good:
    run US-00 production/admission work
```

Current broad assumption:

```txt
us00_cost_current(m) ~= K_m × G_market
```

Target active-good assumption:

```txt
us00_cost_target(m) ~= K_m × G_a
```

### US-10 same-market requests

```txt
for each country present in this market:
  for each generated or active good:
    run US-10 same-market consumption work
```

Current broad assumption:

```txt
us10_cost_current(m) ~= K_m × G_market
```

Target active-good assumption:

```txt
us10_cost_target(m) ~= K_m × G_a
```

So one detailed promoted market in the target shape costs roughly:

```txt
local_market_cost_target(m) ~= L_m + K_m + 2 × K_m × G_a
```

Where:

```txt
L_m = locations scanned to build countries_present_in_market
K_m = countries present in the promoted market
G_a = active goods in the promoted market after filters/cache
```

The formula is not a benchmark. It is a work-shape estimate that tells a developer which axis is expensive before they start editing code.

## Orchestration comparison

| Solution | Dominant shape | Order of magnitude | Reading | Risk |
|---|---|---|---|---|
| Current state country + broad pipelines | `monthly_country_pulse -> country-markets capacity -> US-00 all-goods -> separate US-10` | `O(C * M_c + C * M_c * G_market + resolver scans)` | Costly baseline; several US may revisit the same axes | Caches prepared outside the market/trade container |
| Ownership-split target | `country prep -> promoted-market local branch -> country-scope trade pass` | `O(C * M_c) + O(P * K_m * G_a) + O(C * T_country)` | Recommended target: explicit market-local owner and explicit trade owner | Requires a robust promotion definition, owner guard, and trade-owner definition |

The trade pass is intentionally not filtered down to a promoted market. It must be country-scoped and assignment-gated to avoid double accounting and to keep future trade systems such as US-17 and US-20 visible.

## Expected order of magnitude

Without profiling EU5 directly, a reasonable sizing is:

| Situation | Current broad state | Ownership-split target | Expected gain |
|---|---|---|---|
| Small campaign / few active goods | Tens of thousands of logical monthly iterations | A few thousand plus trade pass cost | `~5x` to `~20x` on market-local work |
| Medium campaign with many markets but few human-relevant markets | Hundreds of thousands to a few million | Tens of thousands plus trade pass cost | `~10x` to `~100x` on market-local work |
| Large campaign / strict audit / all-goods | Several million, plus rescans by US | Hundreds of thousands if `P << M`, plus trade pass cost | `~10x` to `~50x`; less if everything is promoted |
| Well-filtered Performance Mode | Still costly if broad pipelines do not all respect the same filter | `P * K_m * G_a` for local work, plus country-scope trade pass | Potentially `~100x` on goods/local branches; trade cost depends on assignment density |

The key point is that `P` must remain much smaller than `M` in Performance Mode, and `G_a` must remain smaller than `G_market` thanks to active-good lists.

If Normal Mode promotes all current-country markets, the gain is mostly maintainability/cache ownership rather than spectacular runtime reduction, but it still prevents each US from rebuilding its own world.

## Review sizing assumption

Reuse the Q4 sizing assumptions:

| Symbol | Review value | Meaning |
|---|---:|---|
| `G_market` | `60` | Candidate / produced goods per market |
| `M` | `100` | Total markets |
| `C` | `800` | Countries traversed by full monthly country pulse |
| `P_normal` | `100` | Retained/promoted markets in Normal mode |
| `P_performance` | `5` | Likely retained/promoted markets in Performance mode |
| `K_m` | `40` | Countries present in a promoted market |
| `G_a` | `10` | Active goods in a promoted market |
| `T_country` | variable | Assigned trade candidates for one country |

These are sizing assumptions for reasoning. They are not a claim about a specific save file until runtime counters confirm them.

## Raw comparison

| Scenario | Normal, 100 markets | Performance, 5 markets | Reading |
|---|---:|---:|---|
| Current | `800 * 100 * 60 = 4,800,000` | `4,800,000` if broad pipelines remain all-axis | Worrying baseline |
| Ownership-split target | `80,000 prep + 100 * 40 * 10 + C*T_country` | `80,000 prep + 5 * 40 * 10 + C*T_country` | Buys shared local cache and explicit trade ownership |

The raw current estimate uses:

```txt
C * M * G_market = 800 * 100 * 60 = 4,800,000
```

The ownership-split target separates the cheaper prep axis from the heavy local axis:

```txt
C * M = 800 * 100 = 80,000 prep iterations
P_normal * K_m * G_a = 100 * 40 * 10 = 40,000 local active-good iterations
P_performance * K_m * G_a = 5 * 40 * 10 = 2,000 local active-good iterations
```

## Refined comparison

With `K_m = 40` present countries and `G_a = 10` active goods:

| Scenario | Refined formula | Logical iterations | Gain vs current |
|---|---|---:|---:|
| Current | `C * M * G_market` | `4,800,000` | `1x` |
| Ownership-split target, normal | `C * M prep + P_normal * K_m * G_a + C*T_country` | `80,000 + 40,000 + C*T_country` | `~40x` before trade pass cost |
| Ownership-split target, performance | `C * M prep + P_performance * K_m * G_a + C*T_country` | `80,000 + 2,000 + C*T_country` | `~58x` before trade pass cost |

The normal target is:

```txt
120,000 + C*T_country
```

The performance target is:

```txt
82,000 + C*T_country
```

The `C*T_country` part is deliberately separated because the country-scope trade pass is a different ownership surface from the promoted-market local branch.

## Tick-time interpretation

If the current ModeU5 monthly tick is about `5s` and the broad loop cost is the dominant cost, the refined sizing gives this rough loop-only upper-bound estimate before trade-pass and engine overhead:

```txt
normal target:      5s * 120,000 / 4,800,000 ~= 0.125s
performance target: 5s *  82,000 / 4,800,000 ~= 0.085s
```

That is the optimistic loop-only estimate, not a promise for the whole EU5 tick.

A safer practical estimate is:

| Assumption | Approximate optimized tick |
|---|---:|
| ModeU5 broad loop is almost all of the `5s` tick | `~0.2s` to `~0.8s` |
| ModeU5 broad loop is about half of the `5s` tick | `~2.5s` to `~3.0s` |
| Vanilla/engine overhead already consumes most of the `5s` tick | Much smaller visible gain |

Use this as an order-of-magnitude planning estimate until profiling counters measure the actual share of time spent in ModeU5 loops, engine overhead, and trade handlers.

## Current state assessment: Q4.1 and Q5.1

| Topic | Original situation | Current state | Intermediate conclusion |
|---|---|---|---|
| Dispatcher ownership | Broad country pulse hid market-local ownership | Live cycle separates promoted-market local and country trade-owner passes | Good structural improvement |
| Market-local branch | Risk of repeated market mutation | `every_market_center_in_country` owns the local branch | Correct direction |
| Countries-present cache | Could be recomputed or approximated | Built once from `every_location_in_market` into `cbp_countries_present_in_market` | Good work-cache factorisation |
| Capacity | Could be confused with mutation | Capacity remains a prerequisite and country-market relation | Good separation |
| Generated goods | All-goods scan remains expensive | Still all-goods inside detailed markets | Accept for correctness; optimize later with active goods |
| Trade | Could be mixed with market-local work | Kept as country-owned `every_trade` pass | Correct separation |
| Measurement | Mostly qualitative before | PR126 counters expose markets, country passes, goods scans, trade passes | Good enough for shape proof, pending clean runtime logs |

## Target direction

The target is not to remove loops. The target is to put each loop under the correct owner.

```txt
monthly_country_pulse
  -> country prerequisites
  -> promoted-market local branch once per market-center owner
       -> countries present in that market
       -> generated or active goods for US-00 / US-10
  -> country-owned trade pass
  -> validation / reconciliation
```

Future optimization order:

1. Prove ownership correctness: each market-local branch runs once per market.
2. Measure the loop shape with counters.
3. Reduce detailed markets through Performance mode.
4. Only then reduce generated-good scans with active-good work lists.
5. Keep stock writes behind central operators.

## Anticipated benefits

| Benefit | Why it matters | Measure |
|---|---|---|
| Less duplicated market-local work | Avoids repeating a market branch for every country present | `cache_rebuilds_per_market ~= 1` |
| Reduced detailed work in Performance mode | Cuts the largest market × country × goods multiplier | Normal good scans > Performance good scans |
| Cleaner ownership model | Junior developers know where to place new logic | Diagram nesting matches code nesting |
| Safer active-good optimization later | Avoids skipping business-required goods too early | Compare good scans before/after active-good list |
| Trade safety | Trade work stays country-owned and inter-market | Trade passes stable when detailed markets change |

## Practical rule for junior developers

Before changing code, write the loop formula.

For the highlighted section:

```txt
for each detailed promoted market p:
  countries cache     -> location scan for that market
  capacity refresh    -> K_m
  US-00 goods work    -> K_m * G_market today, K_m * G_a as target
  US-10 goods work    -> K_m * G_market today, K_m * G_a as target
```

Then ask:

```txt
Can I reduce P, the number of detailed promoted markets?
Can I reduce accidental repeats of the same market?
Can I reduce G_market toward G_a safely with an active-good list?
```

The safest first win is reducing detailed markets and accidental repeats. The riskiest first win is reducing generated goods, because it can silently skip a good that still needs production, demand, validation, or reconciliation.

## Design decision

The promoted-market local target is preferable because it makes `P`, `K_m`, and `G_a` explicit for heavy local work.

The country-scope trade pass remains separate because `every_trade` is confirmed on country scope and should process assigned trades once, not as a market-local iterator.

Even when the full cost includes a preparation phase and trade pass, this creates shared context for US-00, US-10, validation, debug, and future US without double-counting market-local mutations.

## Closure criteria

Q4.1 is an intermediate checkpoint. It is good enough when:

```txt
Q5.1 nested loop ownership matches the code
Normal mode does more detailed/goods work than Performance mode
Performance mode keeps the controlled request satisfied
Trade-owner pass remains one pass in both modes
Runtime logs are clean enough to trust the counters
```

It is not fully closed until active-good filtering, cache ownership, clean-log proof, and full regression proof have landed or have explicit follow-up issues.
